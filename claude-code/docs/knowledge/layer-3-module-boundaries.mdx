## 边界原则

1. 先按能力定位模块，再进入具体文件。
2. 优先修改领域内已有入口，不跨层直接访问内部细节。
3. 工具、Provider、MCP、UI、远程控制各自有独立测试区域，改动时补到最近的测试集合。
4. 反编译代码里存在超长文件，改动要小而准，避免顺手格式化大文件。

## 修改路径选择

| 要做的事 | 推荐路径 |
| --- | --- |
| 新增斜杠命令 | 先看同类 `src/commands/<name>/`，再接入命令注册点 |
| 新增内置工具 | 先定义工具实现于 `packages/builtin-tools/src/tools/<ToolName>/`，再检查 `src/tools.ts` 组装方式 |
| 调整模型兼容 | 先定位 Provider 转换层，再看 `src/services/api/claude.ts` 请求组装 |
| 改权限行为 | 先改规则解析或 handler，再改 UI 展示 |
| 改 REPL 输入体验 | 先从 `src/screens/REPL.tsx` 找事件入口，再下钻到 `src/components/PromptInput/` |
| 改远程控制 UI/server | 优先在 `packages/remote-control-server/` 内闭环，必要时再改 CLI bridge |

## 不建议跨越的边界

| 不建议做法 | 更稳的方式 |
| --- | --- |
| UI 组件直接拼 API 请求 | 通过 QueryEngine/query 链路传递 |
| 工具实现直接读取 REPL 状态 | 用 ToolUseContext、权限上下文或显式参数 |
| Provider 适配散落在业务调用点 | 收敛到 `src/services/api/` 或 `packages/@ant/model-provider/` |
| 命令实现直接操作远程 server 内部状态 | 经 bridge/acp/server 已有服务接口 |
| 在 `utils` 里堆新业务规则 | 放到具体领域目录，命名体现业务含义 |

## L3 维护规则

新增顶层能力、迁移 package、拆分/合并模块、改变测试归属时，更新本页。每一行都应能回答“我要改这里，先看哪里，测哪里”。
