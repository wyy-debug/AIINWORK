## 决策记录原则

1. 只记录会影响后续开发判断的内容，不记录普通任务流水。
2. 每条决策必须包含日期、背景、决定、影响范围和后续动作。
3. 能链接源码、测试或文档时必须链接路径。
4. 决策可以被新决策替代，但不要直接删除历史。

## 当前决策

### 2026-04-26：新增开发知识五层架构

背景：仓库已有大量文档和学习笔记，但后续开发需要一个固定入口，把“先看哪里、怎么定位、怎么验收、怎么沉淀”统一起来。

决定：新增 `docs/knowledge/`，按五层组织开发知识：

| 层级 | 用途 |
| --- | --- |
| L1 项目入口层 | 项目事实、目录坐标、常用命令 |
| L2 运行链路层 | 启动、对话、工具、Provider、远程控制链路 |
| L3 模块边界层 | 能力到目录/测试的映射 |
| L4 开发作业层 | 开发、测试、文档、验收流程 |
| L5 决策沉淀层 | 长期取舍和后续判断 |

影响范围：`docs/knowledge/`、`docs.json`。

后续动作：开发中一旦发现模块边界或测试归属不准确，优先更新 L3；一旦形成长期架构判断，补充到本页。

### 2026-04-26：区分运行时五层架构和开发知识五层架构

背景：`docs/introduction/architecture-overview.mdx` 已经讲了 MTL-Code 的运行时五层架构，如果再写一份同名架构容易混淆。

决定：运行时架构继续归 `docs/introduction/architecture-overview.mdx`；开发知识架构归 `docs/knowledge/`。两者互相引用，但职责不同。

影响范围：文档导航、后续文档命名、开发者阅读路线。

后续动作：新增运行时细节时更新 introduction/conversation/tools/context 等既有文档；新增开发流程和知识索引时更新 knowledge。

### 2026-04-26：知识事实来源顺序

背景：仓库包含源码、测试、文档、学习笔记和聊天上下文，容易出现多个版本的说法。

决定：事实来源优先级为：源码 > 测试 > docs 正式文档 > learn 学习笔记 > 临时讨论。文档必须尽量带源码路径。

影响范围：所有知识维护工作。

后续动作：当文档与源码冲突时，以源码为准，修正文档。

## 决策模板

```md
### YYYY-MM-DD：一句话说明决策

背景：为什么需要做这个选择。

决定：我们选择什么，不选择什么。

影响范围：涉及哪些目录、命令、文档、测试或行为。

后续动作：谁在后续开发中需要注意什么。
```

## L5 维护规则

当一次改动改变了长期约束、模块职责、默认流程或未来开发判断，就在本页追加一条。追加时写清楚日期，不覆盖旧决策。
