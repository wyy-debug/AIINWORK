## 为什么要单独建知识架构

仓库里已有 `docs/introduction/architecture-overview.mdx`，它讲的是 MTL-Code 的运行时五层架构：交互层、编排层、核心循环层、工具层、通信层。

本目录讲的是开发知识五层架构。它不替代已有白皮书文档，而是给后续开发提供一个固定的知识入口：新人先看第 1 层，定位需求看第 2/3 层，开始编码看第 4 层，做完决策沉淀到第 5 层。

## 五层模型

| 层级 | 名称 | 回答的问题 | 维护位置 |
| --- | --- | --- | --- |
| L1 | 项目入口层 | 这个仓库是什么，怎么启动，关键资料在哪 | `docs/knowledge/layer-1-orientation.mdx` |
| L2 | 运行链路层 | 一次 CLI 启动、一次对话、一次工具调用怎么流转 | `docs/knowledge/layer-2-runtime-flows.mdx` |
| L3 | 模块边界层 | 要改某类能力，应该碰哪些目录，避开哪些边界 | `docs/knowledge/layer-3-module-boundaries.mdx` |
| L4 | 开发作业层 | 开发、测试、文档更新、验收按什么流程做 | `docs/knowledge/layer-4-development-playbook.mdx` |
| L5 | 决策沉淀层 | 为什么这样设计，后续遇到同类问题如何继承判断 | `docs/knowledge/layer-5-decision-memory.mdx` |

## 使用路线

第一次接手仓库：先读 L1，再读已有的 `learn/LEARN.md` 和 `docs/introduction/architecture-overview.mdx`。

要改启动、命令、REPL、对话循环、工具、Provider：先读 L2 确认链路，再读 L3 找模块边界。

要开始写代码：按 L4 的作业清单走，优先跑最小相关测试，再逐步扩大到 typecheck/lint/test。

做出新的架构选择：把选择、原因、影响范围写入 L5。不要只留在聊天记录或临时笔记里。

## 知识更新规则

1. 改代码入口、核心链路、模块边界时，同步更新 L2 或 L3。
2. 改开发命令、测试策略、发布流程时，同步更新 L4。
3. 引入新模式、废弃旧路径、改变长期约束时，同步更新 L5。
4. `learn/` 保持学习笔记属性，`docs/knowledge/` 保持开发索引属性，两者互相链接但不混写。
5. 代码仍然是最终事实来源；文档必须带回源码路径，不写无法追溯的抽象描述。
